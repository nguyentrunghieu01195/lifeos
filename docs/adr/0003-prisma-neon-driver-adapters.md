# ADR 0003 — Prisma with driver adapters: Neon in production, node-postgres in development

**Status:** Accepted · **Phase:** 1

## Context

The database is Neon PostgreSQL and the runtime is Vercel serverless. Classic TCP connection pooling fits serverless poorly, and development environments (including restricted sandboxes) may not have raw TCP egress at all.

## Decision

- **Prisma ORM** with `driverAdapters`:
  - Production (`*.neon.tech` or `DATABASE_DRIVER=neon`): `@prisma/adapter-neon` over the Neon serverless driver (HTTP/WebSocket fetch-based transport).
  - Development: `@prisma/adapter-pg` over node-postgres against any local Postgres; `pnpm db:local` boots a zero-install embedded Postgres.
  - Selection is automatic from the `DATABASE_URL` host, overridable via `DATABASE_DRIVER`.
- Client generated to `src/generated/prisma` (gitignored, regenerated by `postinstall`); accessed only through `getDb()` in `src/lib/db.ts`, which is **lazy** so builds succeed on machines without secrets, and cached on `globalThis` to survive dev hot reload.
- Prisma is pinned to the mature v6 line deliberately; upgrading majors is a scoped decision, not a drive-by.
- Migrations: `prisma migrate dev` against a local/dev database creates SQL committed to the repo; production applies the same SQL with `prisma migrate deploy` against Neon. Schema evolution is strictly additive per phase.

## Consequences

- No TCP sockets in production and no pool exhaustion under serverless concurrency.
- `pg` stays out of the serverless bundle (`serverExternalPackages`) and is never loaded when the Neon driver is selected.
- Migration deploys need a Neon connection from CI or a developer machine — documented in the README deployment steps.
